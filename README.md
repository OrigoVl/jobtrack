# JobTrack — динамічний трекер пошуку роботи (React + Node + SQLite + AI)

Повноцінний легкий full-stack застосунок, що вирішує реальну задачу: **аналізує вакансії та CV, показує прогалини й попит ринку, тренує до співбесід і допомагає з резюме/листами.** Побудований на твоєму стеку зростання: **React + TypeScript + Node.js + SQLite (+ опційно LLM)**.

> **Вимога:** Node.js **≥ 22.5** (краще 24 LTS) — бекенд використовує вбудований модуль `node:sqlite`, тож окрема БД-залежність не потрібна.
> **Пакетний менеджер:** [pnpm](https://pnpm.io) (workspace-монорепо `client` + `server`). Встанови: `corepack enable` (йде разом з Node) або `npm i -g pnpm`.

## Що вміє (v1)

- **🌐 Будь-яка професія** — з LLM навички та **професія/роль визначаються з CV й вакансій** (не лише IT: дизайн, маркетинг, аналітика тощо), і під цю роль підлаштовуються всі AI-поради. Офлайн — fallback на словник IT-технологій.
- **📋 Вакансії** — CRUD, редагування прямо в таблиці (включно з посиланням), **кольорове маркування статусу** (від нейтрального "Хочу подати" через холодні "в процесі" й теплі "близько до фіналу" до зеленого "Оффер"/червоного "Відмова"/сірого "Пауза" — і в таблиці, і кольоровим індикатором колонки/рамки картки в Канбані), **автопідтягування стеку/рівня/fit за посиланням** (з будь-якого публічного сайту вакансій — LinkedIn, Djinni, robota.ua, jobs.dou.ua тощо) одразу при додаванні/зміні URL чи імпорті — окремий клік "Спарсити" більше не обов'язковий, **імпорт з DOU-експорту** (встав HTML → витягне посилання й одразу проаналізує кожну) та **імпорт/експорт JSON** у форматі зовнішнього трекера (`{company, pos, level, fit, status, applied, next, notes, url}`) — можна вести файл окремо (напр. в іншому AI-чаті) і просто "скинути" його в застосунок: вакансії з тим самим `url` (або компанією+позицією) оновляться, решта додасться.
- **🔔 Нагадування** — опційні браузерні Web Notifications про прострочені/сьогоднішні «наступні кроки» (раз на день, лише за явним дозволом користувача).
- **🔍 Аналіз вакансії** — встав текст → визначає **навички і рівень** (LLM для будь-якої галузі, офлайн — словник), рахує **збіг/прогалини** під твій профіль; з LLM — ще й розумне резюме вимог.
- **🎯 Skill-radar** — графік «твої навички vs попит ринку» (рахується з реального стеку доданих вакансій).
- **📊 Аналітика** — поточна воронка подач + **чесна воронка "коли-небудь досягли етапу"** (з журналу історії статусів, не лише поточний знімок) + попит на технології.
- **🧠 Навчання** — **розумні флеш-картки (SRS, інтервали як в Anki)** + **drill-режим**: 89 практичних задач (JS/TS/React/SQL/Node/NestJS/алгоритми/System Design), фільтри за темою й складністю, відмітка «розвʼязано», **JS-пісочниця з запуском коду**, **прогресивні AI-підказки** та **генерація карток і задач під твою роль/прогалини** (доповнює пул для будь-якої професії).
- **🎤 Мок-інтерв'ю** — симуляція співбесіди: випадкова добірка питань і задач із таймером.
- **🗺️ Роудмапа** + **📅 Інтенсив 21 день** — трекери навчання з персистентним прогресом.
- **🧩 Pet-проєкти** — драбина з 4 проєктів із чек-лістами Definition of Done.
- **📄 CV** — аналіз резюме проти попиту ринку + рекомендації, генератор Skills, **cover letter** (текст вакансії — ручний ввід, **вибір із вакансій у трекері** або **посилання з автозавантаженням тексту сторінки**) та **експорт у PDF**.
- **🏢 Компанії** — нотатки й банк питань «що спитали тут».
- **🗂 Канбан вакансій** — drag-and-drop карток між статусами.

## Швидкий старт

```bash
# з кореня репозиторію — встановлює й client, і server одразу (pnpm workspace)
pnpm install
cp server/.env.example server/.env   # (опційно) впиши OPENAI_API_KEY, щоб увімкнути AI
                                      # два рівні моделі: *_MODEL (швидка) і *_MODEL_SMART (якісні поради/оцінки/генерація)

# піднімає бекенд (:3001) і фронтенд (:5173) одночасно
pnpm dev
```

Відкрий **http://localhost:5173**. База (SQLite) створюється автоматично й засівається 16 вакансіями з твоєї таблиці.

Інші корисні команди з кореня: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm format`,
`pnpm test:coverage` (юніт/компонентні тести + звіт покривності), `pnpm test:e2e` (Playwright,
потребує попереднього `pnpm build` — піднімає прод-білд на `:4173` і ганяє ключові флоу).

### Прод-режим (один процес)

```bash
pnpm build                     # збере client у client/dist
pnpm --filter jobtrack-server start   # сервер сам віддасть фронтенд на http://localhost:3001
```

### Docker (одна команда)

```bash
docker compose up --build      # застосунок на http://localhost:3001
```

Multi-stage образ збирає фронтенд і запускає API, що роздає статику. БД (SQLite) зберігається у Docker-волюмі `jobtrack-data` (шлях задається змінною `DB_PATH`), тож дані не втрачаються між перезапусками. LLM-ключі — через змінні оточення в `docker-compose.yml`.

## AI-режим (опційно)

Без ключа все працює в **офлайн-режимі** (аналіз за словником технологій, шаблонні листи). Щоб увімкнути розумні функції — впиши у `server/.env`:

```
LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
```

Підтримується і Anthropic (`LLM_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=...`).

`server/src/config/env.ts` валідує `.env` через Zod одразу при старті (fail-fast): некоректний
`LLM_PROVIDER` чи інша змінна — застосунок впаде з чітким повідомленням, а не мовчки піде в офлайн.

### Оптимізація LLM-запитів (швидкість / точність / вартість)

- **Два рівні моделі** (`tier: "fast" | "smart"` у `chat()`): `"fast"` — дешева модель для
  екстракції/форматування (навички з тексту, домен кандидата, короткий summary вакансії,
  пріоритизація дій), `"smart"` — сильніша модель лише там, де реально потрібна глибша логіка
  (`reviewCv`, `matchCv`, cover letter, парсинг CV у структуру, оцінка мок-інтерв'ю, генерація
  задач/карток). Раніше кілька задач форматування/сумаризації (порада в `/cv/analyze`, "Фокус
  тижня") без потреби викликали `"smart"` — переведено на `"fast"` без відчутної втрати якості.
- **Паралелізація незалежних викликів**: `/cv/upload` і `/vacancies/analyze` раніше робили 2-4
  LLM-запити послідовно (`await` один за одним), хоча запити не залежали один від одного —
  тепер ідуть через `Promise.all`, що майже вдвічі скорочує час очікування користувача.
- **Кешування за хешем вхідних даних** (`cache: true` у `chat()`, або власний кеш у kv-сховищі
  для `extractSkills`/`detectDomain`/`getDynamicKnowledge`): ідентичний вхід не платить за LLM
  двічі; кеш самоінвалідується — зміна тексту/моделі дає новий ключ.
- **Одна автоматична повторна спроба** на транзієнтні помилки провайдера (`429`/`5xx`) з коротким
  фіксованим backoff (400мс) — переживає короткочасні збої без відчутної втрати швидкості;
  постійні помилки (`401`/`404` тощо) не ретраяться, щоб не витрачати зайвий раунд-тріп.
- **Timeout за рівнем моделі**: `"fast"`-запити (проста екстракція) фейляться швидше
  (`LLM_TIMEOUT_MS_FAST=15000`) і падають на офлайн-евристику, ніж `"smart"`-запити (складна
  структурована генерація, `LLM_TIMEOUT_MS=30000`).
- **Логування помилок провайдера і обрізаних JSON-відповідей** (`finish_reason`/`stop_reason`),
  бюджет `maxTokens` підібраний під розмір очікуваної відповіді (напр. `parseCvDocFromText`
  збільшено з 1500 до 2600 — насичене CV з кількома місцями роботи реально не вміщалось).
- Вхідні тексти (CV, вакансія) завжди обрізаються перед відправкою в LLM (`.slice(...)`) —
  недорого й передбачувано по токенах незалежно від того, скільки текст містить у БД.
- Видалено непідключений (dead code) ендпоінт `/llm/rewrite` — не викликався з клієнта.

### Алгоритмічні покращення (не-LLM, детерміновані)

Крім LLM, кілька задач розв'язані класичними, добре обґрунтованими алгоритмами з інформаційного
пошуку/ML — швидше й дешевше за LLM-виклик там, де завдання не потребує "розуміння" тексту,
лише точний/наближений математичний сигнал. Усі — offline-тестовані (жодної мережі в юніт-тестах).

- **FSRS** (`server/src/modules/study/fsrs.ts`) — замінив спрощений SM-2 (`ease`/`interval`,
  бінарна оцінка "пам'ятаю/не пам'ятаю") у SRS-флешкартках (`/study/grade`). Той самий алгоритм,
  на який перейшов Anki: 3-компонентна модель пам'яті (Difficulty/Stability/Retrievability) замість
  одного "ease factor" дає точніші інтервали повторення. UI тепер має 4 кнопки оцінки (Знову/
  Важко/Добре/Легко) замість 2 — потрібно для повного FSRS-рейтингу.
- **TF-IDF ранжування** (`server/src/modules/jobs/job-ranking.ts`) — `/jobs/search` раніше
  сортував зовнішні вакансії лише за `matchCount` (лінійна к-сть тегів, що збігаються з
  профілем); DOU не віддає теги взагалі, тож DOU-вакансії ніколи не могли бути ранжовані.
  TF-IDF рахує документ з POSITION+тегів і важить рідкісні терміни вище за часті — DOU-вакансії
  тепер теж отримують реальний relevance-сигнал із заголовка.
- **Fuzzy-matching / відстань Левенштейна** (`server/src/shared/fuzzy-match.ts`) — офлайн-словник
  технологій (`tech-dict.ts`) раніше ловив лише точні regex-аліаси; типова друкарська помилка
  ("Dockr", "Kubernets") пропускалась повністю. Фолбек-шар толерує невеликі відхилення (порі
  масштабується з довжиною слова — короткі слова взагалі не толеруються, щоб не плодити фолс-
  позитиви), і лише для термінів, які точний словник НЕ знайшов.
- **Ймовірнісний fit-score** (`server/src/modules/vacancies/vacancy-text.ts`) — `computeFit()`
  раніше рахував АБСОЛЮТНУ кількість збігів/прогалин (5 match/5 gap = "high"; 0 match/2 gap =
  "med" — обидва результати вводили в оману). Тепер — частка (зважена попитом навички на ринку,
  якщо доступна мапа попиту) крізь логістичну функцію навколо 50% — 0 match ГАРАНТОВАНО не
  вище "low".
- **Recency-weighted попит ринку** (`server/src/shared/demand.ts`) — `demandMap()` раніше важив
  кожну вакансію однаково незалежно від віку; вакансія з мертвого ринку (стек, який компанія вже
  не набирає) назавжди займала місце в попиті нарівні зі свіжою. Експоненційне згасання за часом
  (half-life 90 днів) — свіжий попит переважує застарілий.
- **SimHash-дедублікація** (`server/src/modules/jobs/job-dedupe.ts`) — та сама вакансія, опублікована
  одночасно на кількох агрегаторах під РІЗНИМИ URL, раніше проходила в список стільки разів,
  скільки джерел її підхопили (дедуп був лише за точним URL). SimHash стискає company+position у
  64-бітний відбиток; near-duplicate — мала відстань Геммінга між відбитками, без парного
  порівняння повного тексту.
- **Векторні embeddings** (`server/src/llm/embeddings.ts`) — OpenAI `text-embedding-3-small` для
  СЕМАНТИЧНОЇ схожості CV↔вакансія (`semanticFit`, лише в інтерактивному `POST /vacancies/analyze`,
  де результат одразу видно користувачу в аналайзері) — доповнення до tech-словника: ловить
  смислову близькість навіть без жодного спільного tech-терміну (напр. "будував REST API на
  Node.js" ↔ "backend-розробник з досвідом побудови масштабованих сервісів"). Дешевше за LLM
  chat-виклик на порівняння — ембединг рахується й кешується один раз, порівняння двох текстів —
  це косинусна схожість двох масивів чисел без мережі. Доступно лише для OpenAI-провайдера
  (Anthropic не має публічного embeddings API тут); без ключа/з Anthropic — `semanticFit: null`,
  не впливає на основний (deterministic, offline-тестований) `fit`. **Свідомо НЕ рахується** у
  `quickAnalyze()`/`tryAutoEnrichStack()` (фонове автозбагачення при створенні/редагуванні
  вакансії, single/bulk re-parse, DOU/JSON імпорт) — там результат нікуди не йде (не показується,
  не зберігається в БД), тож рахувати його там означало б платити за embeddings-виклик заради
  значення, яке одразу відкидається.
- **Funnel-конверсія та середній час у статусі** (`server/src/db/vacancy-history.ts`,
  `GET /analytics`) — двічі використовує ту саму `vacancy_status_history` (журнал зміни статусів,
  вже наявний для чесної воронки `funnelReached`), але рахує з неї два нові похідні сигнали:
  (1) `conversion` — яка частка вакансій, що дійшли до етапу N, дійшла й до N+1 (класична
  funnel-метрика, без запиту до БД — рахується з уже завантажених `funnelReached`-лічильників);
  (2) `stageDurations` — середня різниця в днях між сусідніми записами історії ОДНІЄЇ вакансії
  (той самий принцип, що в survival-аналізі "time in state") — показує, на якому етапі кандидат
  чи рекрутер найдовше тримає паузу, чого не видно зі статичних лічильників. Обидва — детерміновані,
  offline-тестовані, показані на сторінці «Аналітика» (`client/src/features/analytics/charts.tsx`).

## Логування

Структуроване JSON-логування на `pino` (у dev — людяний кольоровий вивід через `pino-pretty`,
у прод — чистий JSON у stdout, готовий для будь-якого лог-агрегатора без додаткової обробки).

- **`pino-http`** логує кожен HTTP-запит (метод/шлях/статус/час відповіді) з унікальним `reqId`.
- **`AsyncLocalStorage`** (`core/request-context.ts`) прокидує той самий `reqId` у глибокі
  сервіси без прямого доступу до `req` (LLM-клієнт, автозбагачення вакансій тощо) через
  `contextLogger()` — усі логи одного запиту користувача зкорельовані одним `reqId`.
- **`redact`** (`core/logger.ts`) — глобальний захист-за-замовчуванням: `Authorization`/`Cookie`/
  `x-api-key` заголовки та поля `password`/`apiKey` ніколи не потраплять у лог, навіть якщо
  колись з'явиться auth і хтось необдумано залоге `req` цілком.
- **Глобальні `unhandledRejection`/`uncaughtException`** (`index.ts`) — несподіваний виняток
  поза Express-запитом логується структуровано (з повним контекстом), а не губиться в
  неструктурованому stderr; на `uncaughtException` процес свідомо завершується (стан після
  такого винятку непередбачуваний) — supervisor (Docker/pm2) підніме новий.
- **"Тихі" зовнішні збої тепер логуються замість мовчазного `null`**: автозбагачення стеку
  вакансії за URL (`tryAutoEnrichStack`), пошук вакансій у зовнішніх агрегаторах (Remotive/
  Arbeitnow/DOU), health-check БД (`pingDb`) і масові операції (import-json, fetch-all) —
  усі мають `warn`/`error`-лог із причиною (URL, HTTP-статус, помилка) замість "просто не
  спрацювало, без пояснень". Рівні підібрані свідомо: `debug` для очікуваних/нормальних
  ситуацій (SSRF-блок явно внутрішньої адреси), `warn` для реальних збоїв зовнішніх джерел,
  `error`/`fatal` — для власних непередбачених/критичних станів.
- **Спрацьований rate-limit** (`aiLimiter`/`apiLimiter`) тепер логується (`warn`, з `ip`+`path`) —
  раніше клієнт бачив тост про помилку, а на сервері не лишалось жодного слідy про можливий
  runaway-цикл чи спробу спалити платну LLM-квоту.

### Куди відправляти логи в проді

Застосунок пише структурований JSON у stdout — сумісно з будь-яким колектором без змін коду.
Варіанти залежно від масштабу (для персонального інструмента з одним інстансом):

- **[Axiom](https://axiom.co/)** — рекомендація за замовчуванням: щедрий безкоштовний план,
  нативний pino-транспорт (`@axiomhq/pino`), швидкий пошук/дашборди по JSON-полях (`reqId`,
  `model`, `status` тощо) без окремої інфраструктури.
- **[Better Stack Logs](https://betterstack.com/logs)** (ex-Logtail) — теж простий pino-транспорт,
  зручний безкоштовний план, плюс готові алерти (напр. сплеск `"LLM API error response"`).
  Хороша альтернатива Axiom.
- **Self-hosted, без стороннього SaaS**: якщо деплой у Docker — достатньо
  **[Dozzle](https://dozzle.dev/)** (легкий read-only веб-UI над `docker logs`, нуль конфігурації)
  для персонального використання; для повноцінного стеку з дашбордами/алертами — Grafana Loki +
  Promtail (важче в налаштуванні, доцільно лише якщо вже є Grafana для іншого).

Жодний із цих сервісів не підключено в коді — потребує власного акаунта/API-ключа власника
застосунку; коли буде готовий ключ, додати транспорт у `core/logger.ts` — питання кількох рядків.

## CI та якість коду

GitHub Actions (`.github/workflows/ci.yml`) на кожен push/PR у `main` ганяє два джоби:

1. **Lint · Typecheck · Test · Build** — `lint` → `typecheck` → `test:coverage` (юніт/компонентні
   тести з v8-звітом покривності + **baseline-пороги** в `vitest.config` — CI впаде, якщо покривність
   опуститься нижче зафіксованого рівня) → `build`, для client і server (pnpm workspace, кеш store).
   Звіти покривності та білд-артефакти заливаються як CI-артефакти.
2. **E2E (Playwright)** — окремий джоб (запускається після першого), піднімає прод-білд і
   прогонить ключові наскрізні флоу (завантаження CV, керування Kanban-дошкою з клавіатури,
   генерація cover letter, чекбокс/toggle прогресу в Роудмапі й 21-денному плані, імпорт вакансій
   з JSON-файлу, збереження посилання на вакансію) у Chromium,
   примусово в офлайн-режимі LLM (швидко, детерміновано, без залежності від платних API).
   Тести виконуються **послідовно** (`workers: 1`) — усі специфікації діляться однією БД одного
   запущеного сервера, а Роудмапа/План21 будуються динамічно з поточного стану вакансій, тож
   паралельний запуск разом із тестом, що додає вакансію, ламав би розрахунки інших тестів.

Dependabot (`.github/dependabot.yml`) щотижня пропонує оновлення npm-залежностей,
Docker-базового образу й GitHub Actions.

Сервер захищений `helmet()` (security-заголовки, включно з реальним Content-Security-Policy —
`script-src 'self'`, `style-src-elem` без `'unsafe-inline'` — інжект `<style>`-блоку заблоковано,
лише `style-src-attr` дозволяє inline `style=""` для кількох динамічних progress-барів; білий
список лише для Google Fonts) і глобальним rate-limit на `/api` (600 запитів/15хв на IP, health
виключено) — щоб баг у фронтенді чи зловживання платними LLM-викликами не поклали сервіс. Лічильники
rate-limit зараз у пам'яті процесу (свідомо: один Node-процес на один SQLite-файл); при переході на
multi-instance деплой — `server/src/core/rate-limit.ts` перше місце, яке треба буде підключити до
спільного сховища (Redis). Додатково AI-ендпоінти (LLM-виклики: рев'ю CV, cover letter,
генерація drill/карток тощо) мають окремий, суворіший ліміт (30 запитів/15хв на IP) — саме вони
коштують реальних грошей на OpenAI/Anthropic, тож їх варто обмежувати жорсткіше за дешеві
CRUD-запити. Виклики до LLM-провайдерів мають timeout (30с) — щоб зависла відповідь провайдера
не вішала запит користувача назавжди — і кожна помилка/таймаут логується з `reqId` поточного
HTTP-запиту (наскрізна кореляція через `AsyncLocalStorage`, `server/src/core/request-context.ts`),
навіть попри те, що LLM-клієнт не має прямого доступу до `req`. Завантаження файлів (`multer`)
обмежене конкретними типами (PDF/DOCX/DOC/TXT/ZIP) — рання відмова 400 замість непередбачуваної
поведінки парсера. CORS відкритий для всіх origin за замовчуванням (auth/cookies немає), або
обмеж через `CORS_ORIGIN` у `.env` (список origin через кому). `trust proxy` вимкнено за
замовчуванням і вмикається явно через `TRUST_PROXY`, лише якщо застосунок реально стоїть за
reverse-proxy/LB. Docker-образ запускає рантайм-процес від непривілейованого користувача (не root).

TypeScript: `noUncheckedIndexedAccess` увімкнено на сервері (індексований доступ до масивів/
об'єктів типізується як `T | undefined`, компілятор ловить пропущені null-перевірки), версія
TS вирівняна між client і server.

Graceful-деградація без LLM-ключа (offline fallback) — контракт, на який покладається кожен
AI-ендпоінт — покрита прямими тестами (`server/src/llm/client.test.ts`,
`server/src/modules/knowledge/knowledge.service.test.ts`): без ключа `chat()` детерміновано
повертає `null` без жодного мережевого виклику, а сервіси (напр. `knowledge.service.ts`) прозоро
falls back на статичний контент.

Поля вакансії `applied`/`next` (дата подачі й дата наступного кроку) валідуються на сервері
як порожній рядок або строго `РРРР-ММ-ДД` (`server/src/shared/validation.ts`), а на клієнті —
`<input type="date">`: аналітика (`/api/insights/focus`) і дашборд рахують "протерміновані"/
"найближчі" кроки порівнянням цих полів як рядків (`v.next < today`), тож довільний вільний
текст у цьому полі раніше тихо ламав сортування й детекцію без жодної помилки. Поле `applied`
(дата подачі), яке раніше існувало в моделі даних, але не мало UI для редагування, тепер
редаговане в таблиці вакансій і показує кількість днів очікування відповіді (>14 днів без
відповіді на активному етапі — підсвічується й потрапляє в «Фокус тижня» як дія «поштовхни»).

Кожна зміна статусу вакансії журналюється в `vacancy_status_history`
(`server/src/db/vacancy-history.ts`) — без цього поточна колонка `status` просто
перезаписується, тож "воронка подач" бачила б лише знімок "де вакансія зараз": вакансія,
відхилена на "Тех.співбесіді", зникала б з цього етапу статистики, ніби через нього й не
проходила. `/api/analytics` тепер повертає й `funnelReached` (скільки вакансій коли-небудь
досягли етапу) поряд із поточним `funnel`.

Імпорт/експорт вакансій у форматі зовнішнього JSON-трекера (`POST /vacancies/import-json`,
`GET /vacancies/export`) — `upsert` за `url` (або, якщо url немає, за парою company+position,
без урахування регістру): існуючі вакансії оновлюються, нові додаються; статус кожного
елемента валідується так само суворо, як і форма ручного редагування, а некоректні елементи
партії не зупиняють імпорт решти — повертаються в `errors` з індексом і причиною.

**Автозбагачення стеку за посиланням** (`tryAutoEnrichStack`,
`server/src/modules/vacancies/vacancy-analysis.service.ts`) тепер триггериться автоматично —
не лише вручну через "🔗 Спарсити" — щойно з'являється/змінюється `url` вакансії: при ручному
створенні (`POST /vacancies`), редагуванні (`PUT /vacancies/:id`, коли URL щойно вписали в
таблиці), імпорті з DOU-експорту (кожна щойно додана вакансія) і JSON-імпорті (лише для нових
елементів — наявні при ресинку не чіпаються, щоб не затерти те, що вже уточнили вручну).
Функція **best-effort і ніколи не кидає**: заблокований SSRF-захистом хост (внутрішня/локальна
адреса — той самий захист, що і в ручному "Спарсити", див. нижче), мережева помилка, таймаут чи
порожня сторінка тихо повертають `null`, і основна операція (створення/імпорт) все одно
завершується успішно.
Bulk-ендпоінти (`/vacancies/import`, `/vacancies/import-json`) через це тепер під `aiLimiter`
(як і `/vacancies/fetch-all`) — вони можуть зробити багато LLM-викликів за один запит.

**Кольорове маркування статусу** (`client/src/shared/status-tone.ts`) — єдине джерело правди
для кольорів статусу вакансії (`bg-…`/`text-…`/`border-…` класи для `<select>` у таблиці,
`bg-…-500` для індикатора-крапки поряд із назвою колонки в Канбані, `border-l-…` для лівої
рамки картки). Прогресія кольорів навмисно семантична: нейтральний slate ("Хочу подати") →
холодні sky/indigo/violet/fuchsia (в процесі, від першого відгуку до тестового завдання) →
теплий amber ("Фінал") → emerald/rose/zinc для явних завершень (Оффер/Відмова/Пауза). Якщо
додаєш новий статус у `STATUSES` (`client/src/shared/types.ts`), онови й цю мапу — є фолбек на
нейтральний slate (`DEFAULT_STATUS_*`), тож відсутність кольору для нового статусу не ламає UI,
але виглядатиме як "невідомий" до оновлення.

**Лоадери під час збереження/операцій.** `Btn` (`client/src/shared/ui.tsx`) підтримує проп
`loading` — показує вбудований SVG-спінер (`Spinner`), автоматично дизейблить кнопку і виставляє
`aria-busy`. Використовується для всіх мутацій на сторінці вакансій: додавання (обидві кнопки —
в шапці й у порожньому стані), імпорт з DOU-експорту, імпорт JSON. Для точкових операцій, де
один mutation-хук обслуговує багато рядків/карток одночасно (редагування чи видалення конкретної
вакансії в таблиці, drag-and-drop/клавіатурне перетягування картки в Канбані), використовується
scoping за `mutation.variables` — TanStack Query зберігає аргументи останнього виклику, доки той
триває, тож можна показати спінер саме в тому рядку/картці, що зберігається/видаляється, а не в
усіх одразу. Це особливо важливо тепер, коли збереження URL синхронно чекає на автозбагачення
стеку (реальний мережевий запит на сторінку вакансії) — без індикатора користувач не розумів, що
застосунок щось робить, а не завис.

**Баг: автопідтягування стеку працювало лише для `jobs.dou.ua`, хоча користувач хотів парсити
з будь-якого джерела.** SSRF-захист (`assertSafeVacancyUrl`,
`server/src/shared/validation.ts`) раніше був жорстким allowlist'ом на один домен — блокував
LinkedIn, Djinni, robota.ua, Indeed і будь-який інший сайт вакансій. Замінили на загальний
SSRF-захист: дозволений будь-який публічний https-хост, блокуються лише очевидні
внутрішні/локальні цілі — `localhost`/`*.local`/`*.internal`, приватні/loopback/link-local
IP-літерали (в т.ч. `169.254.169.254` — типова адреса cloud-metadata сервісів AWS/GCP/Azure,
популярна ціль SSRF-атак). Це syntax-only перевірка без реального DNS resolve (свідомий
трейдофф для локального однокористувацького інструмента, де URL вводить сам користувач — інакше
асинхронний `dns.lookup()` на кожен виклик ускладнив би контракт і зробив би юніт-тести залежними
від мережі; залишковий ризик — DNS rebinding публічного хоста в приватну IP — прийнятний тут).
`stripHtml`/`extractSkills`/`extractLevel` вже були доменно-незалежними (просто чистять HTML і
шукають технології за словником у всьому тексті сторінки) — єдиним бар'єром був саме allowlist.
Тести: `validation.test.ts` (дозволені довільні публічні хости й IP-літерали, заблоковані
localhost/`*.local`/приватні діапазони/`169.254.169.254`/IPv6-loopback),
`vacancy-analysis.service.test.ts` (успішне збагачення з не-dou.ua домену з мокнутим `fetch`),
`e2e/vacancies-url-enrich.spec.ts` (SSRF-блок на приватну адресу — без реального мережевого
запиту, детерміновано).

**Аудит лоадерів по всьому застосунку.** Пройшлися по всіх сторінках і знайшли кілька кнопок, що
викликають мутацію/мережевий запит без жодного індикатора (ані `disabled`, ані тексту "…"):
збереження профілю на сторінці CV, "+ Додати цю вакансію у трекер" в Аналізаторі, "➕ у трекер"
на кожній картці Пошуку вакансій і "+ Додати"/автозбереження нотаток на сторінці Компаній.
Додали `loading`/`Spinner` за тим самим принципом, що й у вакансіях: де mutation-хук один на
всю сторінку/список (Пошук вакансій, Компанії), скоуpимо `isPending` за `mutation.variables`
(URL вакансії чи `id` компанії — а для кнопки "+ Додати" компанії відсутність `id` і є ознакою
саме ЦЬОГО виклику), інакше спінер блимав би одразу в усіх картках.

**Другий прохід: замінили текст-заміну "…" на справжній анімований `Spinner`.** Багато AI-кнопок
(Конструктор CV, CV, Аналізатор, Тренування, Мок-інтерв'ю, План навчання) під час `busy`-стану
лише міняли текст на "…" чи "⏳ Генерую…" — користувач повідомив, що не розуміє, чи йде процес,
бо ця зміна майже непомітна (текст, а не окрема анімована іконка). Пройшлися по всіх таких
кнопках і передали замість ручного `disabled={busy===…}` + текст-заміни проп `Btn loading={…}`
(лишили динамічний текст типу "Аналізую…" там, де він додає контекст — спінер і зміна тексту не
взаємовиключні). Для двох файлових `<label>` (upload CV, LinkedIn .zip у Конструкторі CV), що
виглядають як кнопки, але не є `Btn`, додали `<Spinner>` вручну поруч із текстом. Регресію на
конкретно скаржену кнопку ("🔎 Поради") покриває `e2e/cv-builder-loading-spinner.spec.ts` —
оскільки офлайн-аналіз у E2E (LLM вимкнено для детермінізму) відповідає майже миттєво, і звичний
клік не встигає "зловити" проміжний стан, тест штучно затримує саме цей запит через
`page.route()`, щоб перевірити появу/зникнення `svg.animate-spin` детерміновано, а не покладатись
на випадковий таймінг мережі.

Мутації з оптимістичним оновленням UI (тумблери в Роудмапі/Інтенсиві-21/Pet-проєктах, оцінка картки в SRS-тренуванні)
свідомо лишили без спінера — там UI вже змінюється миттєво (до відповіді сервера), і додатковий
індикатор лише б заважав, не додаючи інформації.

**Баг: "Поради" повертали generic офлайн-текст навіть із ввімкненим LLM, і без жодного логу
причини** (`server/src/llm/client.ts`, `server/src/modules/cv/cv-analysis.service.ts`,
`server/src/modules/mock/mock.routes.ts`, `server/src/modules/analytics/analytics.routes.ts`).
Три шари однієї проблеми:
1. `callProvider()` у `llm/client.ts` не перевіряв `r.ok` — провайдер, що відповів
   401/404/429/500 (невалідний ключ, rate limit, тимчасова помилка) все одно намагався
   прочитати тіло помилки як успішну відповідь (`d?.choices?.[0]?.message?.content` не існує →
   `text=""`), і викликач бачив те саме `null`, що й при легітимній порожній відповіді — без
   жодного логу причини. Тепер `!r.ok` логує `status` + тіло помилки (`contextLogger().error`) і
   повертає `null` явно.
2. Навіть коли HTTP-статус був 200, `response_format:{type:"json_object"}` в OpenAI гарантує
   СИНТАКСИЧНО валідний JSON лише якщо генерація НЕ обірвалась по `max_tokens` — а `reviewCv`
   (`maxTokens:1200`) і `matchCv` (`maxTokens:1000`) легко перевищували цей бюджет (score+summary+
   3-5 strengths+кілька issues+6-12 keywords+кілька rewrites із повними "before"/"after"
   реченнями). Обірваний JSON тихо провалював `JSON.parse` — `chat()` повертав `null` без жодного
   логу. Тепер: (а) `parseJsonOrLog()` логує `finishReason`/`stop_reason` і хвіст тексту при
   провалі парсингу — видно саме коли причина "length"/"max_tokens"; (б) бюджет піднято до 2200 і
   1800 токенів відповідно — з великим запасом під реальний розмір відповіді.
3. **Головна причина скарги користувача**: коли `chat()` таки повертав `null` (з будь-якої
   причини вище), `reviewCv`/`matchCv`/`mock/evaluate` fallback-гілки повертали
   **`offline: false`** разом із тим самим офлайн-евристичним контентом, що й при
   `llmAvailable()===false`. Клієнт (і сам користувач) фізично не міг відрізнити "це справжній
   AI-рев'ю" від "це generic-заглушка" — саме так виглядало повідомлення з баг-репорту
   (`offline:false` + текст "Увімкни LLM у server/.env", хоча ключ був уже налаштований). Тепер
   ці гілки повертають `offline: true`, а `heuristicReview`/`heuristicMatch` приймають
   `reason: "no-key" | "llm-failed"` і показують РІЗНИЙ текст: "увімкни LLM у .env" лише коли
   ключа справді немає, і "AI тимчасово не відповів, спробуй ще раз" — коли ключ є, але саме цей
   запит не вдався. `analytics.routes.ts` (Фокус тижня) отримав той самий фікс для випадку, коли
   LLM повернув 0 валідних дій. Юніт-тести на новий контракт `callProvider`/`chat()` (не-2xx
   статус, обірваний JSON, валідний JSON) — `server/src/llm/client.test.ts`.

**Cover letter: вибір вакансії з трекера або посилання, а не лише ручний textarea**
(`client/src/features/cv/cv.tsx`). Раніше єдиним способом дати LLM контекст вакансії було
вручну вставити текст у textarea. Додано два додаткові джерела над тим самим textarea (він і
далі редагується вручну — нове лише доповнює, не замінює):
- **`<select>` з вакансіями з трекера** (`useVacancies()`, той самий список, що на сторінці
  "Вакансії") — вибір одразу заповнює textarea компонованим текстом (`vacancyToText`: позиція +
  компанія + рівень + стек + нотатки — той самий набір даних, що вже показує таблиця вакансій),
  а назва компанії передається в `/llm/cover-letter` окремим полем `company` (раніше завжди
  передавалось `""`, лист ніколи не звертався до конкретної компанії).
- **Поле для посилання + кнопка "Завантажити"** — новий ендпоінт `POST /vacancies/fetch-url`
  (`server/src/modules/vacancies/vacancies.routes.ts`) стягує й чистить (`stripHtml`) текст
  довільної сторінки вакансії, не прив'язуючись до вже збереженої в трекері вакансії. На
  відміну від `tryAutoEnrichStack` (best-effort, ніколи не кидає — бо це фонове автозбагачення),
  тут помилка (заблокований SSRF-захистом хост, мережева помилка, надто коротка сторінка) явно
  повертається користувачу через toast — це пряма дія з очікуваним результатом, "тихий null"
  лише сплутав би. Той самий SSRF-захист, що і для автозбагачення стеку (`assertSafeVacancyUrl`).
  Ручне редагування textarea або вибір іншої вакансії скидає прив'язку до попередньо обраної
  (`coverVacId`), щоб не переплутати, чию компанію передати в LLM. Кнопка "Згенерувати лист"
  тепер задизейблена при порожньому тексті вакансії (як і інші "Проаналізувати"-кнопки в
  застосунку). Тести: `e2e/cover-letter-vacancy-picker.spec.ts` (вибір вакансії заповнює
  textarea й розблоковує кнопку; приватна/внутрішня URL блокується з toast, без мережевого
  запиту — E2E лишається офлайн/детермінованим).

**Перекомпоновка Конструктора CV: вкладки "Зміст"/"Дизайн" + прев'ю завжди першим.** Раніше
Appearance/Presets-панелі стояли в тій самій правій колонці ПЕРЕД прев'ю → на екрані воно
опинялось після них, нижче за складку ("превью знизу справа" — скарга користувача). Тепер права
колонка (`lg:sticky lg:top-6`, `client/src/features/cv/cv-builder.tsx`) містить ЛИШЕ
`CvPreviewPanel` — воно завжди перше, sticky й одразу у фокусі. Ліва колонка отримала перемикач
`Segmented` "📝 Зміст" / "🎨 Дизайн" (`useUi("cvbuilder.tab", …)`, персистентний): "Зміст" показує
`BasicInfoCard`/`ExperienceCard`/`ProjectsEducationCard`/`LanguagesCard`, "Дизайн" —
`AppearancePanel`/`LayoutPresetsPanel`. Перемикання вкладки не приховує прев'ю — воно й далі
праворуч, тож зміну шаблону/кольору бачиш одразу, без скролу. Грід-колонки —
`grid-cols-1 lg:grid-cols-[minmax(0,1.4fr)_minmax(0,1fr)]` (не просто `lg:grid-cols-[1.4fr_1fr]`
без `minmax(0,…)` і не `grid` без жодного `grid-cols-*` на мобільній ширині): прев'ю рендерить
iframe фіксованої "сторінкової" ширини 880px (`PAGE_WIDTH`, масштабується лише візуально
`transform`-ом) — без явного `minmax(0,…)` цей фіксований піксельний мінімальний контент
розтягував би track неявного одноколонкового гріда (сайзинг `auto` враховує min-content нащадків)
до 880px і ламав усю мобільну сторінку горизонтальним скролом (класичний CSS Grid "blowout").
Регресію на це покриває `e2e/cv-builder-preview.spec.ts` (перевірка `scrollWidth`/`clientWidth` на
390px-вьюпорті для обох вкладок).

**Прев'ю в Конструкторі CV** (`client/src/features/cv/builder/cv-preview-panel.tsx`) рендерить
CV в iframe ФІКСОВАНОЇ "сторінкової" ширини (`PAGE_WIDTH = 880px` — та сама, що й `max-width`
тіла в `buildCvHtml`), а не в ширині сайдбара: сам контейнер лише візуально масштабується
(`transform: scale()`, обчислений через `ResizeObserver` + обраний зум) під доступне місце.
Завдяки цьому шаблон "Дві колонки" у вузькому сайдбарі виглядає так само, як вийде в PDF, а не
спотворено-стиснутим через reflow вузького iframe. Зверху — бейдж орієнтовної кількості сторінок
при друку (висота контенту з `onLoad` / ~1050px на сторінку A4 — це оцінка, реальний друк
прибирає `max-width` через `@media print`, тож може відрізнятись) і підказка про порожні секції,
що не потраплять у PDF. Кнопка "⛶" і floating-кнопка "👁 Прев'ю" (`lg:hidden`, бо на <lg екранах
прев'ю-колонка не `sticky` і йде після всіх карток редагування) відкривають те саме прев'ю в
fullscreen-модалці.

**Важливий супутній фікс у `client/src/index.css`:** глобальна CSS-анімація появи сторінок
(`main > * { animation: jt-fade-in … both; }`) з `animation-fill-mode: both` лишала на прямому
нащадку `<main>` (кореневому `<div>` кожної фіч-сторінки) computed `transform: matrix(1,0,0,1,0,0)`
**назавжди** — навіть після завершення 0.28s анімації, бо кінцевий keyframe задавав
`transform: translateY(0)` (те саме, що й ідентична матриця, а НЕ буквально `none`). Будь-який
`transform`, відмінний від `none` (включно з ідентичною матрицею), створює новий containing
block для `position: fixed`-нащадків — усі fixed-модалки всередині сторінки (`PhotoCropper`,
fullscreen прев'ю CV) рендерилися відносно цього `<div>`, а не справжнього вьюпорту: не
покривали бічний сайдбар і "плавали" разом зі скролом сторінки замість справжнього fixed.
Прибрано `both` з `animation-fill-mode` (лишився дефолтний `none`) — після завершення анімації
властивості коректно повертаються до неанімованих значень (`transform: none`) без жодної
візуальної різниці. Регресію такого штибу неможливо побачити в jsdom/vitest (немає реального
layout/CSS-каскаду) — тому саме на це є E2E (`e2e/cv-builder-preview.spec.ts`), що перевіряє
`boundingBox()` fullscreen-модалки відносно вьюпорту.

**PDF без системного заголовка/підвалу друку.** Chrome/Edge за замовчуванням малюють на кожній
сторінці друку дату+назву документа зверху і URL+номер сторінки знизу — це рендериться в полях
сторінки, зарезервованих під друк. `buildCvHtml`/`exportPdf` (cover letter) тепер додають
`@page{margin:0}` — без полів для них просто немає місця, і вони зникають без потреби вручну
знімати галочку "Заголовки та підвали" у вікні друку (в деяких браузерах, напр. Safari, вона
може лишатись — про це попереджає `title`-тултип на кнопках "⬇️ PDF"). Власний відступ від краю
паперу тепер задає `padding: 14mm 12mm` у `body` при друку (замість поля сторінки, яке ми
прибрали).

### Відомі, свідомо прийняті ризики

- **`react-router` (7.18.1) має CVE** (CSRF bypass у RSC/data-mode, пофіксили лише в 8.3.0,
  GHSA-qwww-vcr4-c8h2). Реального ризику це не несе: застосунок — звичайний client-side SPA
  (`BrowserRouter`), RSC/server actions не використовує. Апгрейд до v8 відкладено свідомо: `react-router-dom`
  не має релізу v8 (пакети злили в один `react-router`), і сам `react-router@8` вимагає **React ≥19.2.7**
  (зараз React 18.3.1) — тобто це не point-фікс, а окрема мажорна міграція (React 18→19 + зміна імпортів
  `react-router-dom` → `react-router`/`react-router/dom`), яку варто робити контрольованою окремою ітерацією,
  а не приховано "заодно" з фіксом вразливості.
  **Моніторинг:** окремого ручного відстеження не потрібно — `react-router` НЕ в ignore-списку
  `.github/dependabot.yml` (на відміну від `typescript`), тож щойно вийде реліз, сумісний із
  React 18 (чи коли буде виконана міграція на React 19), Dependabot сам відкриє weekly PR з
  оновленням, і CI (build-and-test + E2E) підтвердить, що апгрейд не ламає застосунок.

## Архітектура

Бекенд структурований **по доменних модулях** (feature-based, у стилі layered-архітектури
NestJS, але без зайвого фреймворк-оверхеду): кожен модуль має тонкий `*.routes.ts`
(parse → delegate → respond) і `*.service.ts`/`*.data.ts` з бізнес-логікою, яку можна
юніт-тестити без Express. Наскрізні речі (БД, LLM, конфіг, http/логер-примітиви,
крос-доменні утиліти) винесені в окремі шари верхнього рівня.

```
jobtrack/
├── Dockerfile, docker-compose.yml   # контейнеризація (multi-stage)
├── server/                  # Node (ESM) + TypeScript + Express + node:sqlite
│   └── src/
│       ├── index.ts         # entrypoint: app.listen()
│       ├── app.ts           # збірка Express-застосунку (middleware → /api → статика → errorHandler)
│       ├── routes.ts        # агрегує всі modules/*/*.routes.ts в один Router
│       ├── config/env.ts    # єдина типізована точка доступу до process.env
│       ├── core/            # http (HttpError/asyncHandler), logger (pino), error-handler
│       ├── db/              # client (з'єднання+схема+сід), types, kv (профіль/прогрес/SRS), helpers
│       ├── llm/             # OpenAI/Anthropic-клієнт з graceful fallback + кеш відповідей
│       ├── shared/          # tech-dict, skill-extraction, validation (DTO+SSRF), demand, hash, slug, upload
│       └── modules/         # по одній теці на домен API:
│           ├── vacancies/   # CRUD вакансій + аналіз тексту вакансії
│           ├── jobs/        # пошук у зовнішніх агрегаторах (DOU/Remotive/Arbeitnow)
│           ├── cv/          # профіль, CV-конструктор, рев'ю/match, LinkedIn-імпорт, upload
│           ├── knowledge/   # статична + LLM-персоналізована база знань
│           ├── roadmap/     # roadmap.sh-стиль карта навичок з реальних даних
│           ├── plan21/      # динамічний 21-денний інтенсив (прогалини: вакансії − CV)
│           ├── study/       # SRS-картки + drills (статичні + LLM-згенеровані)
│           ├── projects/, resources/, companies/, analytics/, writing/, mock/, health/
└── client/                  # React + Vite + TS + Router + TanStack Query
    └── src/
        ├── main.tsx, index.css      # entrypoint
        ├── app/App.tsx              # роутинг (React Router), sidebar/shell, providers
        ├── shared/                  # наскрізні речі, спільні для всіх фіч:
        │   ├── api.ts               # єдиний типізований контракт з бекендом (усі HTTP-виклики)
        │   ├── queries/             # TanStack Query хуки по домену (кеш, інвалідація, оптимістичні мутації)
        │   ├── toast.tsx            # ToastProvider/useToast (легкий, ізольований від даних контекст)
        │   ├── ui-state.ts          # useUi — персистентний UI-стан вкладок (useSyncExternalStore, без Provider)
        │   ├── types.ts             # спільні DTO-типи (дзеркалять бекенд)
        │   ├── ui.tsx                # UI-кіт (Btn, Card, Chip, PageHeader, Skeleton…)
        │   └── view-kit.tsx         # дрібні хелпери, спільні для 2+ фіч (Field, fitTone/fitText)
        └── features/                # по одній теці на домен екрана (дзеркалить server/src/modules):
            ├── dashboard/, vacancies/, jobs/, analyzer/, companies/
            ├── cv/                  # перегляд CV + Конструктор CV (cv.tsx, cv-builder/*)
            ├── knowledge/           # план навчання (learn.tsx)
            ├── roadmap/, plan21/, projects/, resources/, mock/
            ├── study/               # SRS + drills (study.tsx) + JS-пісочниця (runner.ts)
            └── analytics/           # Skill-radar + графіки (charts.tsx, code-split)
```

Дані та мутації йдуть через **TanStack Query** (`shared/queries/*`) — кожен домен (вакансії, профіль,
роудмапа тощо) має власний хук з типізованим ключем кешу; toggle-мутації (статус роудмапи, drill,
чекбокси) роблять оптимістичне оновлення з відкатом при помилці мережі. Немає жодного глобального
"god context" — сторінки підписуються лише на потрібні їм дані, тож зміна одного не перерендерює все.

## Що далі (ідеї для розвитку)

Повноцінний календар співбесід (зараз лише базові Web Notifications про прострочені/сьогоднішні кроки — див. `client/src/shared/notifications.ts`), дедуплікація при ручному додаванні вакансії (зараз SimHash-дедуп є лише для зовнішнього пошуку `/jobs/search` — див. "Алгоритмічні покращення" вище — і за `url`/company+position для імпорту, але не для ручного додавання однієї вакансії).

Векторні embeddings (`llm/embeddings.ts`) уже рахують семантичну схожість CV↔вакансія (`semanticFit`) — логічний наступний крок: зберігати ембединг кожної доданої вакансії (не лише вакансій "з пошуку") і зробити повноцінний семантичний пошук/рекомендації "схожі вакансії" по всій БД, а не лише по одній парі текстів за раз; для цього масштабу вже варто розглянути `sqlite-vec` (розширення SQLite для векторного пошуку) замість брутфорс-косинуса в JS.

`POST /cv/match` (порівняння CV з КОНКРЕТНОЮ вакансією, `cv-analysis.service.ts`) досі не використовує `semanticFit`: коли LLM недоступний, офлайн-фолбек (`heuristicMatch`) рахує лише перетин токенів (Jaccard-подібне відношення), хоча embeddings-схожість (за наявності OpenAI-ключа) дала б значно точніший сигнал навіть у цьому фолбеку — не додано зараз, бо потребує окремого рішення, як поєднати два числа (token-overlap % і cosine similarity) в один `score` без спотворення сенсу існуючих 0-100 балів.

### Міграція на Postgres + auth (запланований крок)

Наразі персистентність — на `node:sqlite` (синхронний API, нуль залежностей). Для мультиюзерності потрібно: (1) винести доступ до БД за async-репозиторій, (2) підключити `pg`/Prisma до сервісу `postgres` (уже описаний у `docker-compose.yml`), (3) додати JWT-auth (login + guard на `/api`) і прив'язати дані до `user_id`. Це свідомо винесено окремо, щоб не ламати наявний робочий шар. Фактично це і є **навчальний Проєкт 2** з інтенсиву — доводячи його, ти закриваєш SQL, Nest, auth і Docker на реальному продукті.
