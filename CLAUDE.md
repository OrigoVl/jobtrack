# CLAUDE.md

Guidance for Claude (Claude Code or any AI agent) working in this repository. For features,
setup, architecture and security details see **`README.md`** — don't duplicate that here, this
file is only about *how to work* in this codebase.

## Stack

React + TypeScript (Vite) client, Node.js + Express + TypeScript server, Postgres via Drizzle ORM
(`server/src/db/schema/`, `drizzle-kit` migrations committed under `server/drizzle/`), optional
LLM (OpenAI/Anthropic) with graceful offline fallback everywhere. pnpm workspace monorepo:
`client/`, `server/`. Requires a reachable Postgres (`docker compose up -d postgres` locally).

## Commands (run from repo root)

```bash
pnpm install          # installs both workspaces
pnpm dev               # server :3001 + client :5173, concurrently
pnpm lint              # eslint, both workspaces
pnpm typecheck         # tsc --noEmit, both workspaces
pnpm test              # vitest unit/component tests, both workspaces
pnpm test:coverage     # same + v8 coverage report (CI enforces baseline thresholds)
pnpm build             # client build → client/dist, then server tsc build
pnpm test:e2e          # Playwright — requires `pnpm build` first, runs against prod build
pnpm format            # prettier --write .
pnpm format:check      # prettier --check . (CI fails if this fails)
```

`husky` + `lint-staged` run `prettier --write` on staged files automatically on `git commit` —
don't skip this with `--no-verify` unless you have a good reason.

## Before considering any change done

Run, in this order, and make sure all are green:

1. `pnpm lint`
2. `pnpm typecheck`
3. `pnpm test` (add/update unit tests for new logic — see "Testing philosophy" below)
4. `pnpm build`
5. `pnpm test:e2e` if the change touches a flow already covered by `e2e/*.spec.ts`, or add a new
   spec if you added a new critical user-facing flow.

CI additionally runs `pnpm format:check` and `pnpm test:coverage` (not plain `pnpm test`), so a
change that adds a meaningful amount of untested code can pass everything above and still fail
there — run those two as well when you've added more than a few lines.

Don't declare a task finished on the basis of "it should work" — actually run the above.

## Architecture conventions (match existing patterns, don't refactor drive-by)

- **Backend**: feature-based modules in `server/src/modules/<domain>/`. Each module: thin
  `*.routes.ts` (parse request → delegate → respond, no business logic) + `*.service.ts`/
  `*.data.ts` (business logic, unit-testable without Express). Cross-cutting stuff lives in
  `core/` (http/logger/error-handler), `db/`, `llm/`, `shared/`, `config/env.ts`.
- **Frontend**: `client/src/features/<domain>/` mirrors the server's `modules/<domain>/`. Data
  fetching/mutations go through `client/src/shared/queries/*` (TanStack Query hooks, one per
  domain, typed cache keys). No global "god context" — pages subscribe only to what they need.
- **Navigation**: related pages are grouped under a *pathless* layout route rendering
  `app/section-tabs.tsx`'s `SectionTabs` (see `app/App.tsx`) — the tab strip wraps its children
  WITHOUT changing any URL, so existing links/bookmarks/e2e specs keep working and every page
  keeps rendering its own `PageHeader` (and whatever controls hang off its `actions` slot). Adding
  a page to an existing section = one entry in that section's `tabs` array plus a label in the
  `sections` i18n namespace; don't thread an `embedded` prop through the page itself. The tabs are
  real `NavLink`s, not `Segmented` — they're navigation, so middle-click/cmd-click/back must work.
  The sidebar is grouped and its `labelKey`s are typed against `nav.json`'s actual shape (a typo
  is a `tsc` error, not a missing string at runtime); `app/mobile-nav.tsx` renders the same
  destinations as four primary tabs plus a "More" sheet below `lg`.
- **Env vars**: never read `process.env` directly outside `server/src/config/env.ts` — add new
  vars to the Zod schema there, they're validated fail-fast at startup.
- **pgvector columns**: a `vector(...)` column (`drizzle-orm/pg-core`) needs the `vector` Postgres
  extension, which plain `postgres:16-alpine` doesn't have — the docker-compose Postgres image is
  `pgvector/pgvector:pg16` specifically so `CREATE EXTENSION vector` (in the migration SQL) works;
  don't revert that image. PGlite-based tests (`db/test-db.ts`) need the same extension loaded via
  `@electric-sql/pglite-pgvector`'s `vector` import passed to `new PGlite({ extensions: { vector } })`
  — without it every integration test that runs migrations fails, not just ones touching the
  vector column. Never `select()`/select-star a table that has a vector column in a repository
  function whose result reaches an API response — project an explicit column list instead (see
  `vacancies.repo.ts`'s `VACANCY_COLUMNS`), or the embedding silently leaks into the JSON response.
- **Drizzle migrations**: `server/drizzle/*.sql` files are generated by
  `pnpm --filter jobtrack-server exec drizzle-kit generate` and committed as-is — a repo hook
  blocks hand-editing a generated migration file, full stop, even to fix something that looks
  trivial. If a schema change needs a one-time DATA backfill that can't be a bare DDL statement
  (e.g. seeding a new first-class table from an existing `user_kv` blob, the way `cv_profiles` was
  backfilled from the old "cvDoc" key), write it as a separate one-off script under
  `server/scripts/` (see `migrate-cv-profiles.ts`, `backfill-vacancy-embeddings.ts`), run manually
  once after the migration applies — never try to smuggle data-migration SQL into the generated
  file. When a new `NOT NULL` column would break `ADD COLUMN` against a non-empty table in
  production (no `DEFAULT`, existing rows), add it nullable instead and enforce non-null at the
  application layer, backfilling via that same one-off script — see `cv_shares.profileId`'s own
  schema comment in `db/schema/app.ts` for a worked example, including why the composite FK stays
  correct with MATCH SIMPLE semantics while some rows are still NULL.
- **New first-class per-user entity vs. a `user_kv` blob**: reach for a dedicated table (own PK,
  real columns) when the data needs more structure than one JSON blob (a name, a position/
  ordering, or its own child rows), needs a `WHERE` on a specific field scanned across ALL users (a
  scheduler's global query), or other tables need to reference it by id (a composite FK). Otherwise
  a `user_kv` row is less ceremony and is the default. See `cv_shares`/`digest_preferences`/
  `saved_searches`/`cv_profiles` in `db/schema/app.ts` for the reasoning behind each specific call.
- **LLM calls**: use `chat()` (`server/src/llm/client.ts`) for plain text, `chatJson<T>(system,
  user, zodSchema, options)` for structured JSON output — it validates with the schema and does
  one self-repair retry on mismatch, don't hand-roll `typeof`/`Array.isArray` narrowing for new
  LLM JSON call sites. Always gate LLM calls behind `llmAvailable()` with a deterministic offline
  fallback — every AI feature in this app must work without a key.
- **Validation**: Zod for external input (env vars, DTOs). All queries go through Drizzle's query
  builder (parameterized by construction) — no raw SQL string concatenation.
- **Multi-tenancy**: every table and repository function takes an explicit `userId: UserId`
  (branded type, `server/src/db/user-id.ts`) as its first argument — produced only by
  `authed()`/`requireAdmin()` (`core/http.ts`, reading a real better-auth session), never read
  from a route/service directly. New repository functions must follow this pattern, not add a
  parameterless "global" query.
- **Every mutation that does a network call needs a loading indicator** — use `Btn`'s `loading`
  prop (`client/src/shared/ui.tsx`), scoped to the specific row/card via
  `mutation.isPending && mutation.variables === …` when one hook serves many list items.
- **Auth**: better-auth (`server/src/auth/auth.ts`) — email+password (email verification
  required) + Google OAuth, admin plugin for the `role` field. `authed()`/`requireAdmin()` are
  the only place a session is read for authorization purposes — no route/repository ever gets a
  `userId` any other way. The one narrow, sanctioned exception is `core/rate-limit.ts`'s
  `perAccountKey()`, which calls `core/http.ts`'s exported `getSessionUserIdForRateLimit()` (the
  same underlying session lookup, not a reimplementation) so the AI rate limiter can bucket by
  account instead of IP — it returns only an id, never the full session, and that id is used
  purely as an opaque bucketing key, never passed into business logic. `core/http.ts` imports
  `auth/auth.js` lazily (dynamic `import()` inside the function, not a static top-level one)
  specifically so modules that only need `HttpError`/`asyncHandler` — and their unit tests —
  don't transitively open a real Postgres connection just by importing this file. A third
  sanctioned resolver is `modules/mcp/mcp.routes.ts`'s bearer-auth verifier, which resolves a
  `UserId` from a personal API token (`api_tokens` table) instead of a session, for MCP clients
  that authenticate as bearer tokens rather than a browser.
- **i18n (client)**: `react-i18next`, one namespace-per-feature JSON pair under
  `client/src/i18n/locales/{en,uk}/<namespace>.json`. A new namespace must be registered in BOTH
  `client/src/i18n/index.ts` (the `resources` object) and `client/src/i18n/i18next.d.ts` (the
  type augmentation) or `t()` won't resolve/typecheck. Reuse `common.json`'s shared keys
  (`actions.*`, `state.*`, `errors.*`) via `useTranslation(["ownNs", "common"])` instead of
  duplicating them. Never translate a persisted wire value (`VacancyStatus`, `Fit`,
  `RoadmapStatus`, tech/skill/company names) — translate its *display* label instead, via a small
  `Record<WireValue, "literal.key">` lookup (see `shared/fit-tone.ts`) when the union is small and
  closed, or the `statusLabel()` / `i18n.t(key as any, {defaultValue})` escape hatch
  (`shared/status-labels.ts`) when it isn't.
- **i18n (server)**: `getLocale()` (`core/request-context.ts`, populated by `app.ts`'s middleware
  from the client's `X-Locale` header) is the only source of the active locale — never read the
  header directly in a route/service. `chat()`'s `outputLocale?: "app" | "en"` (`llm/client.ts`)
  is opt-in per call site: only for prose the UI locale should own (interview feedback, CV
  review, focus-of-week); leave it off for anything persisted/matched by an English identifier
  (`shared/skill-extraction.ts`) or that must follow the *document's* own language, not the UI's
  (CV export, cover letters). Static content (flashcards/drills/knowledge base/resources/pet
  projects) ships as an English file plus a `<name>.uk.ts` sibling with a `get<Thing>(locale)`
  selector (see `study/content.ts`'s `getCards`/`getDrills`) — never a top-level import of one
  file's export into the other; that's a real circular-import bug (see `knowledge-base.ts`'s
  lazily-evaluated `getKbUk()` for the fix) since the two modules import each other's values.

## Testing philosophy

- Unit tests (`vitest`) for **business logic** (services, algorithms, utils) — aim for high
  coverage there. `*.routes.ts` files are intentionally NOT unit-tested (thin by design); their
  behavior is covered by `e2e/*.spec.ts` instead.
- E2E (Playwright) always runs with LLM **offline** (no API keys in CI) for determinism and
  speed — don't write e2e tests that require a real LLM response.
- New algorithmic/business logic → add a `.test.ts` next to it. New critical user flow → consider
  an e2e spec.
- Repository functions that do real Drizzle queries (not pure logic) → an integration test against
  `server/src/db/test-db.ts`'s `createTestDb()` (PGlite — real Postgres semantics, in-process, no
  Docker), with `vi.doMock(".../client.js", () => ({ default: testDb }))` before a dynamic
  `import()` of the module under test. See `companies.repo.test.ts`/`vacancies.repo.test.ts` for
  the pattern — prove multi-tenant scoping actually holds at the SQL level, don't just mock it away.
- **`server/vitest.config.js` caps `maxWorkers` on purpose.** ~21 suites boot their own PGlite
  instance in a `beforeAll`; at vitest's default of one worker per core, a dozen WASM Postgres
  instances start at once and starve each other past the hook timeout. The symptom is distinctive
  and misleading — a *different random handful* of suites fails on each run, always as
  "Hook timed out in Nms", never as an assertion, and every one of them passes when run alone. If
  you see that, it's contention, not a regression; don't go bisecting, and don't raise the cap.
- **A `pnpm test:coverage` failure is not automatically a "lower the threshold" situation.** The
  client report spans every file matched by `include`, so the many UI files no unit test imports
  count as 0% — the thresholds in `client/vitest.config.ts` are a regression gate pinned to that
  reality (see the comment there). Add tests for the logic you introduced; only re-baseline when
  you can show the *measurement* changed, not the coverage.

### E2E specifics

- **A spec that creates rows must `import { test, expect } from "./fixtures"`**, not from
  `@playwright/test`. The suite runs against a PERSISTENT database on an account shared by every
  spec file, so anything left behind is waiting for the next local run; `e2e/fixtures.ts` diffs the
  account's vacancies/CV profiles/contacts/saved searches/calendar events around each test and
  deletes whatever appeared. Getting this wrong doesn't look like state — a second run turns
  `getByRole("option", { name: /Frontend Developer/ })` into a strict-mode violation over three
  identical options, and which spec fails moves as specs are added. CI never sees it (always a
  fresh DB), so it only ever bites locally. A spec that EDITS existing state instead of creating
  rows (a roadmap status, a ticked plan/project item) has to undo that itself — see the
  `afterEach` in `roadmap.spec.ts`/`projects.spec.ts`/`plan21.spec.ts`.
- **Use `e2e/helpers.ts`'s `addVacancy()`** in any spec that just needs a vacancy to exist before
  testing something else. "+ Add vacancy" opens a create form that only saves on an explicit Save
  (it used to POST a placeholder row immediately), so clicking the button and waiting for
  `POST /vacancies` no longer describes the flow — don't re-spell the form out per spec.
- **`playwright.config.ts` raises `API_RATE_LIMIT_MAX`/`AUTH_RATE_LIMIT_MAX` for the run, and must
  keep doing so.** The whole suite is one IP making thousands of calls; at the human-sized default
  the budget runs out partway through and every spec after that point fails with 429s that look
  like unrelated app bugs — with the failing set moving as specs are added or reordered.
- **The CV Builder opens on a first-run start card while its doc is empty**, so the section
  accordions don't exist yet. A spec driving those fields must first give the doc content (seed it
  via `PUT /api/cv/profiles/:id/doc`, the deterministic option on the shared e2e account) or click
  "Fill it in manually". See `cv-builder-tailor.spec.ts` (seeds) and `cv-builder-start.spec.ts`
  (covers the card itself, on a CV profile it creates so no other spec's seeding can affect it).
- The e2e account is **shared across spec files** and several of them seed the default CV profile.
  Anything that depends on "this is empty" needs its own profile/row, not the default one.

## Style

- TypeScript strict mode, `noUncheckedIndexedAccess` on the server — no `any` (use `unknown` +
  type guards or a Zod schema).
- Minimal diffs; match existing naming/module structure; no drive-by refactors unrelated to the
  task at hand.
- Don't add new dependencies unless the task explicitly calls for it — this codebase deliberately
  favors small, hand-rolled solutions (e.g. `chatJson`'s Zod-based retry instead of an LLM SDK/
  orchestrator) over heavier frameworks when the simpler approach covers the actual need.
